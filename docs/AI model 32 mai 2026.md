# AI Model Report – Server Room Failure Risk Prediction

## 1. Introduction

The Server Room Supervision project is a Projet de Fin d'Etudes (PFE) system designed to monitor the operating conditions of a server room. The Laravel production website collects and displays environmental and electrical measurements such as temperature, humidity, airflow, and power usage. These measurements help the operator understand the current condition of the infrastructure, but the Artificial Intelligence (AI) module adds a predictive layer on top of this monitoring system.

The role of AI in this project is to analyze the latest sensor values and estimate whether the current server rack condition is normal, suspicious, or dangerous. Instead of only showing raw measurements, the system produces a risk level, a rack health score, a failure probability, and a recommendation. This makes the dashboard more useful for preventive maintenance because it helps the user interpret technical values and take action before a serious failure occurs.

The AI module is intentionally separated from the Laravel production hosting environment. The Laravel application remains responsible for storing sensor data, exposing secured Application Programming Interface (API) endpoints, saving predictions, and displaying the latest result on the dashboard. The Python AI logic runs outside the Laravel hosting environment because the production host is limited and does not support running a permanent Python model service.

## 2. Problem Statement

Server rooms are sensitive environments where small changes in temperature or electrical load can indicate a future problem. A high temperature may suggest cooling failure, blocked airflow, or excessive heat generated by equipment. A high power usage value may suggest abnormal rack load, overloaded equipment, or an electrical risk. If these conditions are detected too late, they can lead to downtime, equipment degradation, data loss, or emergency maintenance.

Traditional monitoring systems usually show the current values and may trigger threshold-based alerts. This is useful, but it does not fully explain whether a combination of values is unusual compared with normal operating behavior. For example, a temperature that is not yet critical may still be suspicious if it appears together with increasing power usage. Predictive monitoring tries to identify this type of abnormal pattern earlier.

The problem addressed by this AI module is therefore the early detection of server rack failure risk using the latest available temperature and power usage values. The objective is not to replace human maintenance decisions, but to support them with a simple and explainable risk evaluation.

## 3. Objective of the AI Module

The objective of the AI module is to predict the failure risk of a server rack from two input values: temperature and electrical power usage. The current version uses `temperature` from the server room environmental sensor and `power_w` from the power monitoring sensor. The suffix `_w` means watt, which is the unit used to measure active electrical power.

The AI module returns a structured prediction containing the risk level, rack health score, failure probability, anomaly score, main cause, explanation, recommendation, and raw prediction metadata. This output is sent back to Laravel and stored in the `ai_predictions` table. The production dashboard then displays the latest prediction in a dedicated AI card.

This design makes the AI result reusable. Laravel can show it on the dashboard, n8n can use it in automation workflows, and the project report can explain it as a clear predictive maintenance pipeline. In this first version, Laravel does not train or execute the model directly. Laravel only prepares the data, receives the result, stores it, and displays it.

## 4. Selected AI Model: Isolation Forest

The selected machine learning model is Isolation Forest. Isolation Forest is an anomaly detection algorithm, which means it is designed to identify observations that look different from normal behavior. Instead of learning many examples of failures, it learns the structure of normal data and detects values that are easier to isolate from the rest of the dataset.

The basic idea is that abnormal points are usually more isolated than normal points. In a dataset of normal server room conditions, values such as 25 degrees Celsius and 400 W may appear close to other normal points. A value such as 38 degrees Celsius and 1000 W is far from the normal group and should therefore be treated as suspicious or dangerous.

This model is appropriate for a monitoring context because real failure examples are often rare. In many projects, the system has many normal readings but only a few confirmed failure events. Isolation Forest can still be useful in that situation because it does not require a large labeled failure dataset in the same way as supervised classification models.

In this project, Isolation Forest is used as the machine learning part of a hybrid AI system. The model detects abnormal temperature and power patterns, while additional safety rules protect the system from obviously dangerous threshold values.

## 5. Why Isolation Forest Was Chosen

Isolation Forest was chosen because the project is focused on anomaly detection. The goal is not to classify many known failure categories, but to detect whether the current server rack condition is unusual compared with normal conditions. This matches the nature of the available data, where normal readings are easier to collect than real failure examples.

The model is also suitable because it works with a small number of numerical input features. The first version of the AI module uses only temperature and power usage, which keeps the model simple and explainable. This is important for a PFE project because the jury must be able to understand the logic behind the prediction.

Another reason is that Isolation Forest is lightweight. It can run inside a scheduled Python script without requiring a large server or Graphics Processing Unit (GPU). This fits the deployment strategy where GitHub Actions runs the Python prediction script on a schedule and sends the result back to Laravel.

Finally, Isolation Forest is a realistic first step for predictive maintenance. It provides an anomaly score that can later be improved with real historical data from Laravel and MySQL. The current version is a prototype, but the architecture is ready for future improvement.

## 6. Input Features

The current AI model uses two input features.

| Feature | Source | Meaning | Why It Matters |
|---|---|---|---|
| `temperature` | SHT20 RS485 environmental sensor stored by Laravel | Server room temperature | High temperature can indicate cooling stress, blocked airflow, or overheating equipment. |
| `power_w` | PZEM-004T power sensor stored by Laravel | Active electrical power in watts | High rack power usage can indicate abnormal load, electrical stress, or equipment overload. |

Temperature is one of the most important server room indicators. A server rack can become unstable if the cooling system is not sufficient or if heat accumulates around the equipment. Power usage is also important because abnormal consumption may be linked to increased processing load, electrical faults, or hardware stress.

The first version intentionally uses only these two features to keep the AI pipeline simple. This makes the prototype easier to test, document, and deploy. Later versions can add humidity, airflow, voltage, current, frequency, power factor, Central Processing Unit (CPU) usage, Random Access Memory (RAM) usage, and disk usage.

## 7. Output Results

The AI model returns a structured prediction result. Each field has a specific role in the dashboard and in the maintenance decision process.

| Output Field | Meaning |
|---|---|
| `risk_level` | The general risk category. Possible values are `normal`, `warning`, and `critical`. |
| `rack_health_score` | A score from 0 to 100 representing the estimated health of the rack. A higher value means a healthier condition. |
| `failure_probability` | A percentage from 0 to 100 estimating the probability of a failure risk. In the current prototype, this value is rule-based. |
| `anomaly_score` | A numeric value calculated from the Isolation Forest decision function. It represents how abnormal the current input appears compared with the training data. |
| `main_cause` | A short technical cause label explaining the main reason for the prediction. |
| `explanation` | A human-readable explanation of the prediction. |
| `recommendation` | A suggested maintenance action for the operator. |
| `raw_prediction` | Extra metadata about the model result, such as the model name and version. |

The dashboard uses these values to show the latest AI prediction card. The card gives the operator a quick interpretation of the server room condition instead of forcing them to analyze raw values manually.

## 8. Current Hybrid AI Logic

The current AI model is a prototype hybrid AI system. It combines an Isolation Forest anomaly detector with explicit safety rules written with conditional logic. The Isolation Forest part is the machine learning component. It compares the current temperature and power usage against learned normal patterns and produces an anomaly result.

The safety rules are not a weakness; they are a protective layer. In monitoring systems, dangerous thresholds should never be ignored just because a model gives a low-risk output. For example, if the temperature reaches 36 degrees Celsius, the system should classify the situation as critical even if the machine learning model does not detect it correctly. This is especially important in infrastructure supervision, where safety and reliability are more important than model elegance.

The current training data is temporary and small. It represents normal server room values:

```python
NORMAL_TRAINING_DATA = [
    [24.0, 300],
    [25.0, 350],
    [26.0, 400],
    [27.0, 450],
    [28.0, 500],
    [27.5, 550],
    [26.5, 480],
    [25.5, 420],
    [28.5, 600],
    [29.0, 650],
]
```

This dataset is sufficient for a prototype demonstration, but it is not enough to claim that the model is fully trained for production. A future version should train the model using real historical data collected from Laravel and stored in MySQL. This would make the anomaly detection more representative of the real server room.

In the current implementation, `failure_probability` and `rack_health_score` are rule-based values. The `anomaly_score` is calculated from the Isolation Forest decision function and is therefore the direct machine learning score.

## 9. Decision Rules and Risk Levels

The following table summarizes the current risk logic.

| Priority | Condition | Risk Level | Failure Probability | Rack Health Score | Main Cause |
|---|---|---|---:|---:|---|
| 1 | `temperature >= 35` OR `power_w >= 900` | `critical` | 85 | 15 | `high_temperature_or_high_power_usage` |
| 2 | Isolation Forest predicts anomaly OR `temperature >= 30` OR `power_w >= 700` | `warning` | 55 | 50 | `abnormal_temperature_or_power_pattern` |
| 3 | None of the above conditions are true | `normal` | 10 | 90 | `normal_conditions` |

The rules are evaluated by priority. The critical rule is checked first because dangerous values must override all other decisions. The warning rule is checked second and covers both machine learning anomalies and early threshold warnings. If neither rule is triggered, the situation is considered normal.

The three current risk levels are:

| Risk Level | Meaning | Typical Action |
|---|---|---|
| `normal` | The rack condition appears stable. | Continue monitoring. |
| `warning` | The condition is abnormal or close to a risky zone. | Inspect cooling, airflow, and electrical load. |
| `critical` | The condition is dangerous or already outside safe limits. | Take immediate maintenance action. |

## 10. System Architecture

The AI architecture separates the Laravel production system from the Python AI execution environment. This is important because the production hosting environment is limited and does not support running the Python model permanently. Instead of forcing Python into the hosting server, the project uses GitHub Actions as a scheduled runner.

Laravel production remains the central application. It stores the latest sensor readings, exposes secured API endpoints, saves AI predictions, and displays the prediction on the dashboard. The AI service is stored in a separate GitHub repository named `server-room-ai-service`. The Laravel production application is stored in the main repository named `pfe_test1`.

The scheduled production runner is `run_prediction.py`. It runs in GitHub Actions, reads the latest input values from Laravel, executes the model, and sends the result back to Laravel. The FastAPI file `main.py` exposes a local `/predict` endpoint for local testing and development, while the scheduled workflow can run the prediction script directly.

## 11. API Integration

The AI workflow uses two Laravel API endpoints.

| Endpoint | Method | Purpose |
|---|---|---|
| `/api/ai-input/latest` | `GET` | Returns the latest temperature and power usage values from Laravel production. |
| `/api/ai-predictions` | `POST` | Receives the AI prediction result and saves it in Laravel. |

The first endpoint is used by the scheduled Python runner to read the latest available input values. The expected response contains `temperature`, `power_w`, `temperature_recorded_at`, and `power_recorded_at`. These values are then passed to the Isolation Forest model.

The second endpoint receives the prediction result. The submitted data includes the risk level, rack health score, failure probability, anomaly score, main cause, explanation, recommendation, and raw prediction metadata. Laravel stores this result in the `ai_predictions` table and the dashboard displays the latest record.

## 12. Security

The AI endpoints are protected using the `X-Sensor-Token` HTTP header. HTTP means HyperText Transfer Protocol, which is the protocol used by web clients and servers to exchange requests and responses. The token prevents unauthorized clients from reading AI input values or submitting fake prediction results.

The scheduled GitHub Actions workflow does not store sensitive values directly in the repository. Instead, it uses GitHub Secrets. GitHub Secrets are encrypted environment variables stored in the GitHub repository settings. The current workflow uses the secret names `LARAVEL_BASE_URL` and `SENSOR_API_TOKEN`.

The `LARAVEL_BASE_URL` secret tells the Python runner where the Laravel production API is located. The `SENSOR_API_TOKEN` secret is sent as the `X-Sensor-Token` header when calling Laravel. This avoids exposing the real token in the source code.

This security design is simple and appropriate for the current prototype. For a larger production system, additional protections could be added, such as request signing, token rotation, stricter rate limiting, and separate tokens for read and write operations.

## 13. Deployment Strategy

The Python AI model is not hosted directly on the Laravel production hosting environment. The reason is that the hosting environment is limited and does not support running a permanent Python model service. This is common on shared hosting platforms where PHP applications are supported, but long-running Python services are not.

To solve this limitation, the project uses GitHub Actions as a scheduled cloud runner. GitHub Actions can install Python dependencies, execute the AI script, call the Laravel API, and send the prediction result back to Laravel. This allows the AI module to run automatically without requiring a dedicated server.

The Laravel production application remains lightweight. It only exposes secured endpoints and stores the result. This is safer than trying to run the AI model inside the PHP hosting environment. It also makes the architecture easier to maintain because the Laravel project and the AI service can evolve separately.

For local development, the FastAPI file `main.py` can expose the AI model as an API. FastAPI is a Python web framework used to build fast HTTP APIs. This is useful for testing the model manually or integrating it with tools such as n8n. However, the scheduled production runner is `run_prediction.py`, which is designed to run automatically in GitHub Actions.

## 15. Current Limitations

The current AI model is a prototype and should not be presented as a fully trained production-grade model. The training data is temporary and small. It contains a limited set of normal temperature and power usage values, which is enough to demonstrate the architecture but not enough to represent all real server room conditions.

The current `failure_probability` and `rack_health_score` values are fixed rule-based outputs. They are useful for the dashboard and for explaining the prediction, but they are not yet dynamically calculated from a large historical dataset. The `anomaly_score` is the field that comes directly from the Isolation Forest decision function.

The first version also uses only two features: temperature and power usage. It does not yet use humidity, airflow, CPU usage, RAM usage, voltage, current, frequency, or power factor. These missing variables could improve the quality of future predictions.

Another limitation is that the model has not yet been trained with real historical Laravel/MySQL data. A stronger version should export historical sensor readings from Laravel, clean the dataset, train the model with real operating patterns, and then compare model behavior against known incidents or expert-defined risk cases.

## 16. Future Improvements

The most important future improvement is to train the model with real historical sensor data from Laravel and MySQL. This would make the anomaly detection more representative of the real server room. The training data should include normal operating periods, warning periods, and any known incidents.

The model can also be improved by adding more input features. Future versions should consider humidity, airflow, CPU usage, RAM usage, voltage, current, frequency, and power factor. These values would give the model a more complete view of the server room and server rack condition.

The `failure_probability` should later be calculated dynamically from the anomaly score and the learned data distribution. The system could also add an AI confidence value to indicate how reliable the prediction is. Another useful improvement would be a risk trend, showing whether the situation is improving, stable, or becoming worse over time.

The dashboard could be expanded with an AI history chart showing the evolution of risk level, failure probability, and rack health score. Explainability can also be improved with SHAP-style explanations. SHAP means SHapley Additive exPlanations, a method used to explain which features contributed most to a model prediction.

Finally, Isolation Forest can later be compared with other models such as LightGBM or Random Forest. LightGBM is a gradient boosting machine learning framework often used for tabular data. Random Forest is a supervised ensemble model that can be useful if enough labeled failure examples are collected.

## 17. Conclusion

The AI architecture implemented for the Server Room Supervision project is useful, realistic, and appropriate for the current constraints. It adds predictive maintenance capabilities without forcing Python to run permanently on the Laravel production hosting environment. Laravel remains responsible for the production website, database storage, secured APIs, and dashboard display, while the Python AI service runs separately through GitHub Actions.

The current model is a prototype hybrid AI system. Isolation Forest provides the anomaly detection layer, and safety rules guarantee that dangerous values are classified correctly. This is a practical approach for infrastructure monitoring because critical thresholds must always be respected.

The architecture is also scalable. The same API flow can later support a stronger model trained on real historical data. Additional features can be added without changing the general design: Laravel provides the data, the AI service predicts the risk, and Laravel stores and displays the result.

For the PFE, this solution demonstrates both technical feasibility and engineering realism. It shows how a production Laravel application can be connected to an external AI module despite hosting limitations. It also shows that predictive maintenance can be introduced gradually, starting with a transparent prototype and improving it over time with real data.
